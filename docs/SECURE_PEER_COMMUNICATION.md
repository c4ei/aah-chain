# IEUM peer 메시지·화상·원격 도움 보안 설계

## 결론

peer 간 메시지, 음성·화상채팅, 화면 공유와 원격 도움은 구현할 수 있습니다. 그러나
합의·거래 P2P와 같은 채널에 바로 섞거나 통화 내용을 블록에 저장하면 안 됩니다.
`v0.18.0`은 암호화된 WebRTC 연결 협상 신호를 peer 사이에 전달하는 코어와
지갑용 로컬 RPC를 포함합니다. 실제 카메라·마이크·화면 UI와 WebRTC media 처리는
`ieum-wallet`에서 구현합니다.

## 반드시 지킬 원칙

1. 메시지·음성·영상·화면은 체인과 DB에 평문으로 저장하지 않습니다.
2. 연결마다 임시 키를 만드는 종단간 암호화(E2EE)를 사용합니다.
3. 사용자는 상대방의 DID 또는 안전번호를 직접 확인할 수 있어야 합니다.
4. 서버는 연결 중계와 오프라인 암호문 전달만 하며 복호화 키를 갖지 않습니다.
5. 원격 도움은 화면 보기와 원격 제어 권한을 분리하고 매번 사용자가 승인합니다.
6. 파일 전송, 클립보드, 관리자 권한, 키 입력은 기본적으로 금지합니다.
7. 세션이 끝나면 권한과 임시 키를 즉시 폐기하고 자동 재접속하지 않습니다.
8. 개인키·시드 문구·`validator.key`가 보이는 화면에는 원격 제어를 허용하지 않습니다.

## 권장 구조

- 신원 확인: IEUM DID 키와 별도의 통신용 키를 연결해 서명
- 1:1 메시지: Noise 또는 Signal Double Ratchet 계열 E2EE
- 음성·화상·화면 공유: WebRTC DTLS-SRTP
- 연결 협상: 서명된 세션 초대와 짧은 만료 시간
- NAT 통과: STUN 우선, 실패할 때 TURN 중계
- TURN: 영상은 볼 수 없고 암호화 패킷만 전달
- 그룹 통신: MLS(Message Layer Security) 같은 검증된 그룹 키 규격
- 로컬 보관: OS 보안 저장소와 암호화 DB, 사용자가 보관 여부 선택

기존 libp2p QUIC 연결도 전송 구간은 암호화되지만 그것만으로 사용자 신원 확인,
메시지 장기 보안, 다중 기기 키 변경 검증이 모두 해결되지는 않습니다. 통신용
프로토콜과 키 수명 주기를 별도로 둬야 합니다.

## 원격 도움 안전 절차

```text
도움 요청 → 상대 DID 확인 → 1회용 코드 확인 → 화면 보기 승인
→ 필요한 경우에만 제어 승인 → 화면에 항상 공유 표시 → 즉시 종료 버튼
→ 세션 키 폐기
```

원격 도움 프로그램은 다음 기능을 기본 차단해야 합니다.

- 무인 접속과 영구 비밀번호
- 운영체제 로그인 화면 제어
- UAC 또는 sudo 승인 대신 클릭
- 지갑 시드·개인키 입력 화면 캡처
- 검증자 키 파일과 원장 파일 다운로드
- 몰래 실행, 백그라운드 재연결, 세션 녹화

## 단계별 구현 권장

1. `v0.18.0`: 짧은 수명의 암호화 연결 협상 신호 전달
2. 지갑: 통신용 X25519 키, 안전번호 확인, WebRTC 음성·화상
3. 지갑: 차단·신고·키 변경 경고와 선택형 암호화 메시지 보관
4. 명시적 승인형 원격 포인터
5. 제한된 원격 제어와 보안 감사

원격 제어는 가장 위험하므로 외부 보안 감사를 통과하기 전에는 테스트넷에서도
기본 비활성화하는 것이 안전합니다.

## v0.18.0 로컬 RPC

노드는 통신 payload를 복호화하지 않습니다. 지갑이 통신 전용 임시 키로 먼저
암호화한 뒤 `encrypted_payload_hex`에 넣어야 합니다.

- `ieum_sendCommunication`: 대상 peer에게 암호화 신호 전송
- `ieum_pollCommunication`: 현재 노드가 받은 암호화 신호를 한 번 가져옴

허용 종류:

```text
call_invite, call_accept, call_reject
web_rtc_offer, web_rtc_answer, ice_candidate
hangup, encrypted_chat
```

보안 제한:

- 생성 시각부터 만료 시각까지 최대 120초
- 암호문 최대 64KiB
- 메시지 id 재사용 거부
- 발신 PeerId 위조 거부
- 수신함·발신함 각 256개 제한
- RPC 기본 바인딩 `127.0.0.1`; 외부 IP로 바인딩하면 통신 RPC는 강제로 비활성화

v0.18.1부터 모든 노드가 구독하는 공용 통신 topic은 사용하지 않습니다. libp2p
request-response 전용 프로토콜로 대상 PeerId에 직접 보내고 수신 노드가 수락 여부를
응답합니다. 따라서 대상이 아닌 Gossipsub 구독자에게 envelope가 배포되지 않습니다.
다만 직접 연결 피어는 통신 시각과 트래픽 크기를 관찰할 수 있으므로 TURN 운영 정책,
지갑 E2EE 구현과 메타데이터 위협 모델에 대한 외부 보안 감사를 완료해야 합니다.
