# 간헐 접속 클라이언트 설계

## 결론

모바일·웹 지갑은 블록체인 네트워크에 계속 접속할 필요가 없습니다.
필요할 때 연결하고 최신 상태를 안전하게 확인한 뒤 연결을 끊을 수 있습니다.
상시 접속이 필요한 것은 합의를 수행하는 검증자와 네트워크를 제공하는 일부
풀 노드·RPC·부트스트랩 노드입니다.

## 기본 동작

```text
앱 실행
  → 알려진 RPC/라이트 노드 2~3개에 짧게 연결
  → 최신 확정 헤더와 검증자 집합 확인
  → 마지막 저장 높이 이후 헤더만 동기화
  → 필요한 잔액·nonce·거래의 Merkle proof 요청
  → 기기 안에서 proof 검증
  → 거래를 기기 안에서 서명하고 전송
  → 거래 ID와 마지막 확정 헤더를 저장
  → 연결 종료
```

다음에 앱을 열면 저장한 거래 ID의 포함 여부와 확정 상태를 확인합니다.
거래를 보냈다고 바로 성공으로 표시하지 않고 `전송됨 → 블록 포함 → 확정` 상태를
구분해야 합니다.

## 모바일 데이터 최소화

- 전체 블록과 전체 상태를 받지 않습니다.
- 마지막으로 검증한 높이 이후의 헤더만 증분 다운로드합니다.
- 화면에 필요한 계정과 거래의 증명만 요청합니다.
- 동일한 응답은 짧은 기간 로컬 캐시를 사용합니다.
- 새 거래 알림은 가능하면 OS push를 힌트로만 사용하고, 앱이 직접 체인에서
  다시 검증합니다.
- Gossipsub과 DHT 전체에 모바일을 직접 참여시키지 않습니다.

## 안전 조건

간헐 접속이 가능한 것과 서버 응답을 그대로 믿어도 된다는 것은 다릅니다.

1. 앱에 신뢰 가능한 genesis hash 또는 최근 체크포인트를 고정합니다.
2. 최신 확정 헤더에 검증자 `2/3 초과` 서명이 있는지 검증합니다.
3. validator set 변경을 이전에 신뢰한 집합부터 순서대로 검증합니다.
4. 잔액과 nonce는 state root에 대한 Merkle proof로 확인합니다.
5. 가능하면 서로 다른 운영자의 노드 응답을 교차 확인합니다.
6. 오래 접속하지 않은 클라이언트는 validator set 변경 범위가 크므로
   새 신뢰 체크포인트를 안전하게 받아야 합니다.

## 키와 개인정보

- 개인키는 네트워크나 RPC 서버로 보내지 않습니다.
- 거래 서명은 모바일 보안 저장소 또는 기기 내부에서 수행합니다.
- DID·VC 원문도 기본적으로 사용자 기기에 저장합니다.
- 체인에는 발급기관, 상태 root와 폐기 여부 같은 최소 정보만 둡니다.

## 현재 구현 상태

현재 `0.0.3`은 풀 노드 P2P와 합의 코어에 geth 호환 JSON-RPC의
계정·잔액·송금 경로를 결합한 학습·테스트 단계입니다.
모바일 클라이언트가 사용할 헤더 동기화, state root, Merkle proof, 경량 RPC는
아직 구현되지 않았습니다. 따라서 지금 실행 중인 노드를 단순히 잠깐 연결했다
끊는 것은 가능하지만, 그것만으로 안전한 라이트 클라이언트가 완성되는 것은
아닙니다.

## 구현 순서

1. 블록 헤더에 결정론적인 state root 추가
2. `Status`, `GetHeaders`, `GetProof`, `SubmitTransaction` 프로토콜 추가
3. 확정 인증서(commit certificate)와 validator set 변경 증명 추가
4. 계정·nonce·거래 Merkle proof 추가
5. Rust 라이트 클라이언트 코어와 테스트 벡터 작성
6. 코어를 WASM 및 모바일 라이브러리로 빌드
7. TypeScript SDK와 Tauri 모바일 지갑 연결
