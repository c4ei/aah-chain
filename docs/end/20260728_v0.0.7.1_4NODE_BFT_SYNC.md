# IEUM Chain v0.0.7.1 — 실제 4노드 BFT 확정과 신규 노드 동기화

## 버전

- 패키지 버전: `0.7.1`
- 문서 표기: `0.0.7.1`
- 기준 버전: `0.0.6.9`
- 작성일: 2026-07-28
- DB 변경: 없음

## 요청 내용

1. 메모리 단위테스트에 머물던 4노드 BFT를 실제 P2P 실행 경로에 연결
2. 2/3 초과 precommit 뒤에만 블록을 확정·저장
3. 신규 노드가 확정 증명을 검증하며 원장을 동기화
4. 변경 파일만 압축 배포

## 완료한 작업

### RPC와 합의 분리

- `eth_sendTransaction`, `personal_sendTransaction`, `eth_sendRawTransaction`은 거래를
  즉시 블록으로 만들지 않고 mempool에 등록한다.
- 합의가 끝나기 전에는 잔액, nonce, 블록 높이와 디스크 원장을 변경하지 않는다.
- `web3_clientVersion`은 Cargo 패키지 버전을 자동 표시한다.

### 실제 P2P BFT 실행

- P2P wire message에 거래, 서명된 proposal, prevote, precommit을 연결했다.
- 서버는 `--validator-index 1..4`로 서로 다른 테스트 검증자 역할을 실행한다.
- 정렬된 검증자 목록에서 높이와 라운드에 따라 제안자를 교대한다.
- 제안 블록은 이전 해시와 다음 높이를 검사한다.
- 등록 검증자의 Ed25519 서명만 투표권에 포함한다.
- 동일 검증자가 같은 높이·라운드에서 다른 블록에 투표하면 거부한다.
- 전체 투표권의 2/3를 **초과**한 precommit이 있어야 확정한다.
- 동일 가중치 4노드에서는 서로 다른 검증자 3개의 precommit이 필요하다.
- 확정 전 후보 블록은 메모리에만 두고, 확정된 블록만 RPC 원장과 archive에 저장한다.
- 합의 시간 초과 시 다음 라운드로 이동하고 후보 거래를 mempool로 되돌린다.

### 신규 노드 동기화

- 연결 직후 현재 확정 높이 다음부터 동기화를 요청한다.
- 서버는 한 번에 최대 128개, 직렬화 기준 약 1.5MB 이내의
  `FinalityCertificate`를 제공한다.
- 인증서에는 블록, 합의 라운드, 확정 precommit 목록이 포함된다.
- 신규 노드는 다음을 모두 검증한 뒤 블록을 적용한다.
  - 블록 자체 해시
  - 각 precommit 서명
  - 등록 검증자 여부
  - 동일 블록·높이·라운드 여부
  - 중복 검증자를 제외한 2/3 초과 투표권
  - 현재 tip과 연속된 높이 및 previous hash
  - 거래 서명, nonce, 잔액 및 수수료
- 응답이 128개이면 다음 높이를 다시 요청하여 이어받는다.
- 동기화한 블록도 일반 확정 블록과 동일하게 archive에 저장한다.
- `data/ledger/finality-certificates.jsonl`에 확정 증명을 append-only로 기록하여
  서버 재시작 후에도 신규 노드에 제공한다.

### 검증

- 기존 4노드 테스트를 블록 목록 복사가 아닌 확정 인증서 동기화로 변경했다.
- precommit이 2개뿐인 위조/미확정 인증서를 신규 노드가 거부하는 테스트를 추가했다.
- 패치 공백·경로 검사와 압축 무결성 검사를 수행한다.

## 4노드 테스트넷 실행 예

각 노드는 서로 다른 데이터 경로, UDP 포트, RPC 포트와 validator index를 사용한다.
서로 다른 서버라면 P2P 포트는 모두 7001을 사용할 수 있다.

```bash
# 노드 1
./target/release/ieum-chain server \
  --validator-index 1 --port 7001 --rpc-port 8989 \
  --rpc-data-dir data/validator-1 --node-key data/validator-1.node.key

# 같은 PC에서 시험하는 노드 2~4
./target/release/ieum-chain server \
  --validator-index 2 --port 7002 --rpc-port 8990 \
  --rpc-data-dir data/validator-2 --node-key data/validator-2.node.key
```

노드 2~4가 노드 1을 찾도록 각 서버의 bootstrap 설정 또는 `client --peer`에 실제
PeerId가 포함된 QUIC multiaddr를 지정해야 한다. 운영 4서버에서는 방화벽 UDP 7001과
각 서버의 고유 영구 node key를 사용한다.

신규 일반 노드:

```bash
./target/release/ieum-chain client
```

정상 확정 로그:

```text
[BFT 확정] 높이 1, 해시 ..., precommit 3개
```

정상 동기화 로그:

```text
[P2P 동기화 응답] ... 확정 블록: N개
[동기화 완료] 확정 블록 N개 적용, 높이 N
```

## 중요한 제한

이 버전은 **4노드 폐쇄형 테스트넷 검증용**이다. 실제 가치가 있는 자산을 넣는
메인넷 버전은 아니다.

- 검증자 4개의 seed가 재현 가능한 개발용 값이다. 누구나 알 수 있으므로 메인넷 금지.
- validator 설정 변경, epoch, stake, slashing은 아직 없다.
- Tendermint의 locked value/valid value 전체 안전 규칙은 다음 버전 대상이다.
- 합의 WAL은 기존 모듈이 있으나 새 실행 루프의 proposal/vote 송신과 완전히 결합해야 한다.
- sync는 인증서를 검증하지만 snapshot/state root 기반 고속 동기화는 아직 없다.
- Gossipsub 기반 요청/응답이므로 대규모 공개망에서는 전용 request-response 프로토콜로
  변경해야 한다.
- 동기화 인증서 파일은 아직 월별 압축·pruning 대상에 포함되지 않는다.
- server 단일 인스턴스 guard 때문에 한 PC에서 4개 프로세스를 동시에 띄우는 시험은
  guard 포트 분리 옵션을 추가하거나 별도 컨테이너/VM이 필요하다.

## 앞으로 할 작업

### v0.0.7.x 필수 안정화

1. `config/validators.json`과 암호화된 로컬 validator keystore
2. 합의 WAL에 proposal/prevote/precommit 송신 전 fsync 및 재시작 복구 연결
3. locked value, valid value, nil vote와 라운드별 timeout 완성
4. 전용 libp2p request-response sync와 peer별 rate limit
5. sync status, 진행률, peer count를 실제 RPC 값으로 제공
6. state root를 블록 헤더와 확정 인증서에 포함
7. snapshot manifest, chunk hash, 중단 후 이어받기
8. 네트워크 분리, 1노드 장애, 이중투표, 손상 인증서, 재시작 장기 테스트

### 공개 테스트넷 전

1. 고정 개발 faucet/validator 키 제거
2. RocksDB/redb 계열 상태·인덱스 저장소
3. 검증자 설정과 프로토콜 버전의 합의된 업그레이드 규칙
4. telemetry와 `ieum.stat.aah.name`
5. IEUM 전용 explorer
6. PC/모바일 지갑의 암호화 keystore와 로컬 서명
7. 외부 보안 검토와 fuzz/property test

## 완료 기준

운영 서버 또는 서로 다른 VM 4대에서 아래 항목을 반복 확인해야 이 버전의 실환경
검증이 끝난다.

1. 4대 연결 후 거래 100건 이상이 모든 노드에서 같은 높이·블록 해시·잔액으로 확정
2. 임의 1대 중단 상태에서 나머지 3대로 계속 확정
3. 2대 중단 상태에서는 확정이 멈추고 복귀 뒤 다시 진행
4. 신규 노드의 빈 data 디렉터리에서 tip까지 동기화
5. 중간에 종료한 신규 노드가 재실행 후 이어서 동기화
6. 서버 재시작 후 저장한 finality certificate로 신규 노드 동기화
7. 같은 높이에서 3개 미만 precommit 블록이 어느 노드에도 저장되지 않음
